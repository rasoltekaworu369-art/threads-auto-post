## STEP 1｜GitHub にプライベートリポジトリを作る

`gh` コマンドがこの環境に入っていないため、ここは手でやる。

### 1-a. ブラウザで作る

1. https://github.com/new を開く
2. **Repository name:** `threads-auto`
3. **🔴 Private を選ぶ**（`参照/` にボスの文体指紋と実投稿が入っている。Public にした時点で全部公開される）
4. README・.gitignore・license は**どれも追加しない**（ローカルに既にある）
5. **Create repository**

### 1-b. 上げる

作成後の画面に出る URL を使って、ローカルから push する。

```bash
cd "/d/【Rasolte】/Claude/threads-auto" && git remote add origin https://github.com/<あなたのユーザー名>/threads-auto.git && git push -u origin main
```

### 1-c. 上がったか確認

GitHub 上でファイルが **22個** あること、`参照/` が見えることを確認する。

## STEP 2｜Meta アプリを作って Threads のトークンを取る

1. https://developers.facebook.com/apps/ → **アプリを作成** → ユースケースで **Threads** を選ぶ
2. 作成後、**Threads の App ID と App Secret** を使う（アプリが同時に作るもう一方の ID ではない）
3. **アプリのロール → Threads テスター** に自分の Threads アカウントを招待し、Threads 側で**承諾**する
   - 🔴 これで **App Review なしで使える**。審査が要るのは他人のアカウントを扱うときだけ
4. 権限（スコープ）は次の4つを有効にする
   - `threads_basic` / `threads_content_publish` / `threads_manage_insights` / `threads_manage_replies`
5. Authorization Window で認可 → 認可コード（1時間）→ 短期トークン（1時間）→ **長期トークン（60日）** まで交換する
6. `GET /me?fields=id` で **Threads ユーザーID** を取る

### 🔴 トークンの60日問題

長期トークンは60日で**恒久的に**失効する。更新せず60日経つと OAuth からやり直し。事前警告は出ず、ある日 401 になる。
`.github/workflows/refresh-token.yml` が毎週日曜に更新する。**このワークフローを止めてはいけない。**

## STEP 3｜GitHub Secrets を置く

リポジトリの **Settings → Secrets and variables → Actions → New repository secret**

| 名前 | 中身 |
|---|---|
| `THREADS_USER_ID` | STEP 2-6 で取った Threads ユーザーID |
| `THREADS_ACCESS_TOKEN` | STEP 2-5 で取った長期トークン |
| `GH_PAT_FOR_SECRETS` | トークン更新を**自動で**反映したい場合のみ。`secrets:write` 権限の Personal Access Token |

> `GH_PAT_FOR_SECRETS` を置かない運用でもいい。その場合、毎週の更新ワークフローは
> 「更新成功。残り有効期間: 59日」とログに出すだけになるので、**月1回手でトークンを差し替える**。
> PAT を増やしたくないならこちらのほうが安全。ただし**差し替えを忘れると60日で死ぬ**ので、カレンダーに入れること。

## STEP 4｜手動で1本テスト投稿する（自動化の前に必ずやる）

Actions タブ →「Threads 自動投稿」→ **Run workflow**

その前に、テスト用のキューを1本だけ置く。

```bash
cd "/d/【Rasolte】/Claude/threads-auto" && mkdir -p queue && printf '{"date":"TODAY","posts":[{"slot":"test","テーマ":"接続テスト","text":"テスト投稿です。"}]}\n' > "queue/$(date +%F).json" && git add queue && git -c user.name=Rasolte -c user.email=rasolte149511@gmail.com commit -m "テスト用キュー" && git push
```

**ここが通れば、仕組みの一番危ない部分（API の配線）が片付く。** 通らなければログに原因が出る。
確認したら、テスト投稿は Threads 側で消し、`queue/` と `posted/` の該当ファイルも消す。

## STEP 5｜Routine A と C を作る

https://claude.ai/code/routines → **New routine**

| | Routine A | Routine C |
|---|---|---|
| 名前 | Threads 翌日分9本の生成 | Threads 反応の判定と改善案 |
| プロンプト | `運用/Routine_A_生成プロンプト.md` の中身をそのまま貼る | `運用/Routine_C_計測改善プロンプト.md` |
| リポジトリ | `threads-auto` | `threads-auto` |
| 環境 | **Default のまま**（外部APIを呼ばないので許可ドメイン変更は不要） | Default のまま |
| コネクタ | **全部外す** | 全部外す |
| スケジュール | daily を選んで時刻 **23:07** | daily を選んで時刻 **05:07** |
| モデル | 一番強いものを選ぶ | 標準でよい |

- 時刻は**ローカルタイムで入る**。毎時ピッタリは数分遅れるので :07 にしてある
- **2時間おきの投稿は Routine ではなく GitHub Actions がやる**（Routine の最小間隔は1時間で、9回/日の Claude セッションは使用量の無駄）

### 作ったら、まず Run now

自動スケジュールに乗せる前に、Routine A を **Run now** で手動実行して、できた9本を目で見る。
型が9本ぜんぶ違うか、締めが質問/言い切り/労いに3本ずつ割れているかを確認する。

## STEP 6｜朝の30秒ゲート（推奨）

Routine A は前夜に9本を `queue/<日付>.json` に書く。朝それを見て、ダメな本の `text` を `SKIP` に書き換えて push すると、
Actions はその本を飛ばして記録だけ進める。

```bash
cd "/d/【Rasolte】/Claude/threads-auto" && git pull && code "queue/$(date -d tomorrow +%F).json"
```

完全無人でいくなら、このステップを飛ばして2週間走らせ、`reaction-log.csv` の **clicks** で判定する。

## 走り出したあとの確認ポイント

| いつ | 見るもの | 異常のサイン |
|---|---|---|
| 毎朝 | `queue/<今日>.json` が9件あるか | 無い → Routine A が失敗。claude.ai/code/routines で run のログを読む |
| 毎朝 | `posted/<昨日>.json` が9件あるか | 少ない → Actions の失敗。Actions タブのログを読む |
| 毎週 | 「Threads トークン更新」が緑か | 赤 → 🔴 最優先で対処。放置すると60日で全停止 |
| 2週間後 | `reaction-log.csv` の clicks | TOP3の合計が1日20未満 → 仕組みより先に「入れ物」の問題が残っている |

GitHub の接続が切れると Routine は最大72時間スキップし、それを超えると自動 OFF になる（復帰は手動）。
